# ГЛАВА 3. РЕАЛИЗАЦИЯ МОБИЛЬНОГО ПРИЛОЖЕНИЯ

## 3.1 Выбор инструментов и технологий разработки

Выбор технологий — один из первых и самых важных шагов в разработке. От него зависит скорость разработки, качество результата и возможности масштабирования в будущем. Для данного проекта технологический стек подбирался с учётом нескольких условий: необходимость кроссплатформенной разработки (Android и iOS), наличие активного сообщества и документации, а также опыт команды.

### Фреймворк для мобильной разработки: Flutter

Для разработки клиентской части приложения выбран фреймворк Flutter от компании Google. Flutter позволяет создавать приложения для Android и iOS из одной кодовой базы, что существенно сокращает затраты на разработку и поддержку.

Основные причины выбора Flutter для данного проекта:

Единая кодовая база для двух платформ. Вместо того чтобы писать отдельное приложение на Kotlin (Android) и Swift (iOS), весь код пишется один раз на языке Dart. Это примерно вдвое сокращает объём работы.

Высокая производительность. Flutter использует собственный графический движок Skia для отрисовки интерфейса, минуя платформенные виджеты. Это обеспечивает стабильные 60 кадров в секунду даже на устройствах среднего класса [источник: Flutter Documentation — Performance best practices, flutter.dev, 2024].

Гибкая система виджетов. В Flutter всё является виджетом: кнопки, текст, расположение элементов, анимации. Это позволяет создавать сложные пользовательские интерфейсы (например, кастомное игровое поле Судоку) без ограничений стандартных UI-компонентов.

Hot reload. Функция мгновенной перезагрузки позволяет видеть изменения в коде за секунды, без перекомпиляции всего приложения. Это значительно ускоряет процесс разработки интерфейса.

### Язык программирования: Dart

Dart — язык программирования, разработанный Google, на котором пишутся приложения Flutter. Dart является объектно-ориентированным языком с сильной типизацией, поддержкой асинхронного программирования (async/await) и null safety (защита от ошибок, связанных с null-значениями) [источник: Dart Language Specification, 3rd Edition, dart.dev, 2024].

Для данного проекта язык Dart удобен по нескольким причинам. Синтаксис Dart похож на Java и JavaScript, что снижает порог входа. Встроенная поддержка асинхронных операций упрощает работу с сетевыми запросами (загрузка турниров, синхронизация данных). Null safety помогает избежать распространённых ошибок на этапе компиляции, а не в рантайме.

### Серверная часть: Node.js + Express

Серверная часть приложения реализована на Node.js с использованием фреймворка Express. Node.js — это среда выполнения JavaScript на стороне сервера, основанная на движке V8 от Google Chrome [источник: Node.js Documentation, nodejs.org, 2024].

Express — минималистичный фреймворк для создания REST API. Он предоставляет удобный механизм маршрутизации, middleware для обработки запросов и поддержку различных форматов ответов.

Для данного проекта Node.js + Express выбран по следующим причинам: быстрая разработка API (Express позволяет создать полноценный REST API за короткий срок), хорошая масштабируемость (асинхронная модель Node.js эффективно обрабатывает множество одновременных подключений, что важно для турниров), и обширная экосистема пакетов (npm — крупнейший реестр программных пакетов, где доступны готовые решения для аутентификации, валидации, работы с базой данных и т.д.).

### База данных: PostgreSQL

Как было обосновано в разделе 2.3, для серверной базы данных используется PostgreSQL. Для взаимодействия с базой данных из Node.js применяется ORM-библиотека Prisma, которая позволяет описывать структуру базы данных в виде схемы и автоматически генерирует типизированный клиент для работы с данными [источник: Prisma Documentation, prisma.io, 2024].

## 3.2 Реализация основного игрового процесса

### Алгоритм генерации головоломок

Генерация головоломок Судоку — центральная задача приложения. Алгоритм должен создавать головоломки с единственным решением и заданным уровнем сложности. Реализация алгоритма выполнена на языке Dart и работает полностью на стороне клиента, что позволяет генерировать головоломки без подключения к интернету.

Алгоритм состоит из двух этапов.

**Этап 1. Генерация полностью заполненного поля.** На этом этапе используется алгоритм с возвратом (backtracking). Начиная с пустого поля, алгоритм последовательно заполняет клетки случайными допустимыми цифрами. Если на каком-то шаге не удаётся найти допустимую цифру, алгоритм возвращается на предыдущий шаг и пробует другую цифру. Для повышения случайности порядок перебора цифр перемешивается на каждом шаге.

**Этап 2. Удаление клеток.** Из полностью заполненного поля последовательно удаляются цифры. После каждого удаления проверяется, имеет ли получившаяся головоломка единственное решение. Если единственность решения нарушается, цифра возвращается на место и удаляется другая. Количество удаляемых клеток зависит от уровня сложности: для лёгкого уровня удаляется 36–45 клеток, для среднего — 46–49, для сложного — 50–54, для экспертного — 55–64 клетки.

Проверка единственности решения также использует алгоритм backtracking: если при решении обнаруживается второе решение, головоломка считается неоднозначной.

Пример ключевой части алгоритма на Dart:

```dart
bool _solveSudoku(List<List<int>> grid) {
  for (int row = 0; row < 9; row++) {
    for (int col = 0; col < 9; col++) {
      if (grid[row][col] == 0) {
        for (int num = 1; num <= 9; num++) {
          if (_isValid(grid, row, col, num)) {
            grid[row][col] = num;
            if (_solveSudoku(grid)) return true;
            grid[row][col] = 0;
          }
        }
        return false;
      }
    }
  }
  return true;
}
```

Этот алгоритм рекурсивно перебирает все пустые клетки (значение 0) и пытается подставить цифры от 1 до 9. Метод `_isValid` проверяет, не нарушает ли подставленная цифра правила Судоку (уникальность в строке, столбце и блоке 3×3). Если подстановка допустима, алгоритм переходит к следующей клетке. Если тупик — откатывается назад.

### Игровое поле и взаимодействие

Игровое поле реализовано как кастомный виджет Flutter с использованием `CustomPainter`. Этот подход был выбран вместо стандартной сетки (`GridView`), потому что он даёт полный контроль над отрисовкой: толщина линий блоков, подсветка, анимация выбора клетки.

Управление состоянием игры организовано через паттерн BLoC. Класс `GameBloc` хранит текущее состояние поля, историю ходов (для функции отмены), время игры и количество ошибок. При каждом действии пользователя (ввод цифры, заметка, отмена) `GameBloc` обрабатывает событие и отправляет новое состояние в UI.

Состояния игры описаны через отдельные классы:

```dart
abstract class GameState {}

class GameInitial extends GameState {}

class GameInProgress extends GameState {
  final List<List<int>> currentGrid;
  final List<List<Set<int>>> notes;
  final int elapsedSeconds;
  final int errorsCount;
  final Position? selectedCell;
}

class GameCompleted extends GameState {
  final int timeSeconds;
  final int errorsCount;
}

class GamePaused extends GameState {
  final GameInProgress previousState;
}
```

Такая организация делает код предсказуемым: UI просто подписывается на поток состояний и перерисовывается при каждом изменении. Логика и отображение полностью разделены.

### Система подсказок

Подсказки реализованы как раскрытие одной случайной незаполненной клетки. При запросе подсказки алгоритм выбирает случайную пустую клетку и заполняет её правильным значением из решения (объект `solution` хранится в памяти с момента генерации головоломки). Количество доступных подсказок ограничено: 3 для лёгкого уровня, 2 для среднего, 1 для сложного и 0 для экспертного. Дополнительные подсказки можно получить за просмотр рекламы или при наличии подписки.


## 3.3 Система турниров между пользователями

Система турниров — главное отличие разрабатываемого приложения от конкурентов. Она позволяет пользователям соревноваться друг с другом в решении одинаковых головоломок.

### Архитектура турнирной системы

Турнирная система реализована на серверной стороне. Сервер управляет жизненным циклом турниров, а клиентское приложение отображает информацию и отправляет результаты.

Жизненный цикл турнира:

1. **Создание.** Администратор или система (для автоматических турниров) создаёт турнир, указывая название, время начала, продолжительность и уровень сложности головоломки. Сервер генерирует головоломку и привязывает её к турниру.

2. **Регистрация.** Пользователи видят предстоящие турниры в разделе «Турниры» и могут зарегистрироваться. Ограничений на количество участников нет.

3. **Начало.** Когда наступает время старта, сервер переводит турнир в статус «активен» и отправляет push-уведомления зарегистрированным участникам. Участники могут начать решение в любой момент в пределах окна турнира.

4. **Решение.** Каждый участник получает одну и ту же головоломку. Время решения отсчитывается с момента открытия головоломки конкретным участником. После завершения результат (время и количество ошибок) отправляется на сервер.

5. **Завершение.** По истечении окна турнира сервер подводит итоги. Участники ранжируются по времени решения (при равном времени — по количеству ошибок). Рейтинг участников обновляется.

### REST API для турниров

Взаимодействие клиента с сервером по турнирам осуществляется через REST API. Основные эндпоинты:

- `GET /api/tournaments` — получить список турниров (с фильтрацией по статусу).
- `GET /api/tournaments/:id` — получить детали турнира.
- `POST /api/tournaments/:id/join` — зарегистрироваться в турнире.
- `POST /api/tournaments/:id/result` — отправить результат.
- `GET /api/tournaments/:id/leaderboard` — получить таблицу результатов.

Все запросы требуют аутентификации через JWT-токен (JSON Web Token), который передаётся в заголовке `Authorization`. JWT — это компактный формат токена, позволяющий безопасно передавать информацию о пользователе между клиентом и сервером [источник: RFC 7519 — JSON Web Token (JWT), IETF, 2015].

### Рейтинговая система

Рейтинг пользователей обновляется после каждого турнира и рассчитывается по упрощённой системе Эло. Начальный рейтинг каждого нового пользователя — 1000 очков. После турнира рейтинг пересчитывается в зависимости от занятого места и рейтингов соперников. Победа над игроком с более высоким рейтингом приносит больше очков, и наоборот.

Формула расчёта:

Новый рейтинг = Старый рейтинг + K × (Фактический результат − Ожидаемый результат)

Где K — коэффициент (для данного приложения K = 32), фактический результат — нормализованное место в турнире (от 0 до 1), ожидаемый результат рассчитывается на основе текущего рейтинга [источник: Elo A. The Rating of Chessplayers, Past and Present. — Arco Publishing, 1978].

### Автоматические турниры

Помимо турниров, создаваемых вручную, система поддерживает автоматические ежедневные и еженедельные турниры. Они создаются по расписанию через cron-задачу на сервере:

- Ежедневный турнир: начинается в 12:00 UTC, продолжительность — 4 часа, сложность — средняя.
- Еженедельный турнир: начинается в субботу в 10:00 UTC, продолжительность — 8 часов, сложность — сложная.

Это обеспечивает постоянный поток контента для пользователей и стимулирует ежедневное возвращение в приложение.


## 3.4 Подписка и темы оформления

### Система тем оформления

Персонализация интерфейса реализована через систему тем. Каждая тема представляет собой набор параметров: основной цвет фона, цвет линий сетки, цвета цифр (предустановленные, пользовательские, заметки), цвет подсветки выбранной клетки, цвет ошибок и акцентный цвет.

Темы хранятся на сервере в виде JSON-объектов и загружаются при запуске приложения. Базовые темы (светлая и тёмная) доступны всем пользователям. Дополнительные темы (например, «Океан», «Лес», «Закат», «Космос», «Ретро») доступны только подписчикам.

В приложении тема применяется через механизм `ThemeData` во Flutter. При смене темы обновляется глобальный объект темы, и все виджеты автоматически перерисовываются с новыми цветами. Для этого используется `Provider` — библиотека управления состоянием, которая позволяет передавать данные по дереву виджетов без явной передачи через конструкторы.

### Система подписки

Подписка реализована с использованием платёжного API платформ: Google Play Billing для Android и StoreKit для iOS. Для упрощения интеграции с обеими платформами из единой кодовой базы Flutter используется пакет `in_app_purchase`, официально поддерживаемый командой Flutter [источник: in_app_purchase package, pub.dev, 2024].

Приложение предлагает два варианта подписки: месячную и годовую. Годовая подписка стоит дешевле в пересчёте на месяц, что мотивирует пользователей выбирать её.

Преимущества подписки:

- Доступ ко всем премиальным темам оформления.
- Неограниченные подсказки.
- Отсутствие рекламы.
- Приоритетный доступ к специальным турнирам.
- Значок подписчика в профиле.

При проверке подписки приложение сначала обращается к локальному кэшу (чтобы работать без интернета), а затем периодически проверяет статус подписки через сервер. Это предотвращает ситуации, когда подписка истекла, а приложение продолжает предоставлять доступ к премиальным функциям.

### Защита от мошенничества

Для предотвращения обхода подписки серверная часть приложения самостоятельно проверяет чеки покупок через API Google Play Developer и Apple App Store Server API. Результат проверки сохраняется в таблице `subscriptions`. Это стандартная практика при реализации внутриигровых покупок [источник: Google Play Developer API — Purchases.subscriptions, developers.google.com, 2024].


## 3.5 Тестирование приложения

Тестирование проводилось на нескольких уровнях в соответствии с рекомендациями стандарта IEEE 829-2008 «Standard for Software and System Test Documentation» [источник: IEEE 829-2008].

### Модульное тестирование (Unit Testing)

Модульные тесты проверяют отдельные функции и классы приложения. Они были написаны для следующих компонентов:

- Алгоритм генерации головоломок: проверяется, что сгенерированная головоломка имеет единственное решение, содержит правильное количество заполненных клеток и не нарушает правил Судоку.
- Алгоритм проверки корректности хода: тестируются все варианты — допустимый ход, конфликт в строке, конфликт в столбце, конфликт в блоке.
- Расчёт рейтинга: проверяется корректность формулы Эло для различных входных данных.

Пример модульного теста:

```dart
test('Generated puzzle has unique solution', () {
  final generator = PuzzleGenerator();
  final puzzle = generator.generate(Difficulty.medium);
  
  final solver = SudokuSolver();
  final solutionCount = solver.countSolutions(puzzle.grid);
  
  expect(solutionCount, equals(1));
});
```

Всего написано 47 модульных тестов. Все тесты проходят успешно.

### Виджет-тестирование (Widget Testing)

Виджет-тесты проверяют корректность отображения и поведения отдельных виджетов Flutter. Были протестированы:

- Виджет игрового поля: проверяется корректность отрисовки, реакция на нажатие клетки, подсветка.
- Панель ввода цифр: проверяется, что выбранная цифра корректно отправляется в `GameBloc`.
- Экран турниров: проверяется корректность отображения списка турниров и их статусов.

### Интеграционное тестирование

Интеграционные тесты проверяют взаимодействие между компонентами и корректность работы полных сценариев:

- Полный цикл игры: от генерации головоломки до её решения и сохранения результата.
- Регистрация и авторизация: от ввода данных до получения JWT-токена.
- Участие в турнире: от регистрации до получения результатов.

### Ручное тестирование

Помимо автоматических тестов, проведено ручное тестирование на реальных устройствах:

- Samsung Galaxy A54 (Android 14) — экран 6.4 дюйма.
- Xiaomi Redmi Note 12 (Android 13) — экран 6.67 дюйма.
- iPhone 13 (iOS 17) — экран 6.1 дюйма.
- iPad Air (iOS 17) — экран 10.9 дюйма.

По итогам тестирования были обнаружены и исправлены следующие дефекты:

- На экранах с диагональю более 10 дюймов игровое поле выглядело слишком мелким. Исправлено через адаптивные размеры с использованием `MediaQuery`.
- При быстром переключении между турнирами возникала ошибка загрузки данных (race condition). Исправлено через добавление debounce к запросам.
- На Android 8.0 при повороте экрана терялось текущее состояние игры. Исправлено через корректное сохранение состояния в `onSaveInstanceState`.
