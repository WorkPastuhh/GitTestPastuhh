# ГЛАВА 2. ПРОЕКТИРОВАНИЕ МОБИЛЬНОГО ПРИЛОЖЕНИЯ

## 2.1 Архитектура программного обеспечения

При проектировании архитектуры приложения «Судоку» была выбрана клиент-серверная модель. Мобильное приложение (клиент) отвечает за отображение интерфейса и игровой процесс, а серверная часть — за хранение данных пользователей, управление турнирами и синхронизацию между устройствами.

Такой подход продиктован требованиями проекта. Без серверной части невозможно организовать турниры между пользователями, рейтинговую систему и облачную синхронизацию прогресса. При этом основная логика игры (генерация головоломки, проверка решения, заметки) выполняется на стороне клиента. Это позволяет играть в Судоку даже без подключения к интернету.

Общая архитектура приложения включает три уровня:

**Уровень представления (Presentation Layer).** Это пользовательский интерфейс мобильного приложения. Он отвечает за отображение игрового поля, меню, профиля, турниров и настроек. Для построения UI используется компонентный подход: каждый экран состоит из независимых виджетов, которые можно переиспользовать.

**Уровень бизнес-логики (Business Logic Layer).** Здесь сосредоточена основная логика приложения: алгоритм генерации головоломок, проверка корректности хода, подсчёт рейтинга, управление состоянием игры. На стороне клиента бизнес-логика реализована с использованием паттерна BLoC (Business Logic Component), который отделяет логику от представления и упрощает тестирование.

**Уровень данных (Data Layer).** Этот уровень отвечает за хранение и получение данных. На стороне клиента используется локальная база данных для хранения текущей игры и настроек. На стороне сервера — реляционная база данных для хранения профилей пользователей, результатов игр и данных турниров. Взаимодействие между клиентом и сервером осуществляется через REST API.

Принципы проектирования архитектуры основаны на рекомендациях стандарта IEEE 1471-2000 (ISO/IEC 42010:2011) «Systems and software engineering — Architecture description» [источник: ISO/IEC 42010:2011]. Этот стандарт определяет подходы к описанию архитектуры программных систем, включая использование различных представлений (views) для разных заинтересованных сторон.

Разделение приложения на три уровня обеспечивает несколько преимуществ для данного проекта. Во-первых, можно разрабатывать и тестировать каждый уровень независимо. Во-вторых, замена одной технологии на другую (например, смена базы данных) не потребует переписывания всего приложения. В-третьих, при росте количества пользователей можно масштабировать серверную часть, не затрагивая клиентское приложение.


## 2.2 UML-диаграммы приложения

Для визуализации архитектуры и поведения приложения были разработаны UML-диаграммы в соответствии с нотацией UML 2.5 [источник: OMG Unified Modeling Language (UML), Version 2.5.1, Object Management Group, 2017].

### Диаграмма вариантов использования (Use Case Diagram)

Диаграмма вариантов использования описывает взаимодействие пользователей с системой. В приложении выделены два типа актёров: обычный пользователь (игрок) и администратор.

Основные варианты использования для игрока:

- Зарегистрироваться / войти в аккаунт.
- Начать новую игру (выбрать уровень сложности).
- Решить головоломку (ввести цифры, использовать заметки, получить подсказку).
- Просмотреть статистику и достижения.
- Участвовать в турнире.
- Просмотреть рейтинг (личный и глобальный).
- Изменить тему оформления.
- Оформить подписку.
- Редактировать профиль.

Основные варианты использования для администратора:

- Создать турнир.
- Управлять турнирами (редактировать, отменить).
- Просмотреть статистику пользователей.
- Управлять темами оформления (добавить, удалить).

### Диаграмма классов (Class Diagram)

Диаграмма классов отражает структуру приложения на уровне объектов и их взаимосвязей. Основные классы приложения:

**User** — представляет пользователя системы. Атрибуты: id, email, passwordHash, nickname, avatarUrl, rating, createdAt. Связан с классами GameResult и TournamentParticipant.

**Puzzle** — головоломка Судоку. Атрибуты: id, grid (начальное состояние поля 9×9), solution (решение), difficulty (уровень сложности), createdAt. Связан с классом GameResult.

**GameResult** — результат решения головоломки. Атрибуты: id, userId, puzzleId, timeSeconds, errorsCount, completed, finishedAt. Связывает пользователя с головоломкой.

**Tournament** — турнир. Атрибуты: id, title, startTime, endTime, status, puzzleId. Связан с классами Puzzle и TournamentParticipant.

**TournamentParticipant** — участие пользователя в турнире. Атрибуты: id, tournamentId, userId, timeSeconds, errorsCount, rank. Связывает пользователя с турниром.

**Theme** — тема оформления. Атрибуты: id, name, previewUrl, isPremium, colors (JSON-объект с цветовой палитрой).

**Subscription** — подписка пользователя. Атрибуты: id, userId, plan (месячная/годовая), startDate, endDate, isActive.

**Achievement** — достижение. Атрибуты: id, name, description, iconUrl, condition. Связан с пользователями через промежуточную таблицу UserAchievement.

### Диаграмма последовательности (Sequence Diagram)

Для иллюстрации ключевых сценариев были построены диаграммы последовательности.

**Сценарий «Начать новую игру»:**

1. Игрок выбирает уровень сложности на экране главного меню.
2. Клиент вызывает генератор головоломок (PuzzleGenerator), передавая выбранный уровень сложности.
3. Генератор создаёт головоломку и возвращает объект Puzzle.
4. Клиент отображает игровое поле с начальным состоянием головоломки.
5. Клиент запускает таймер.

**Сценарий «Участвовать в турнире»:**

1. Игрок открывает список активных турниров.
2. Клиент запрашивает список турниров у сервера через REST API.
3. Сервер возвращает список турниров со статусом «ожидает начала» или «активен».
4. Игрок выбирает турнир и нажимает «Участвовать».
5. Клиент отправляет запрос на регистрацию в турнире.
6. Сервер регистрирует участника и возвращает подтверждение.
7. Когда турнир начинается, сервер отправляет push-уведомление.
8. Клиент загружает головоломку турнира и начинает игру.
9. После завершения клиент отправляет результат на сервер.
10. Сервер обновляет таблицу результатов турнира.

### Диаграмма состояний (State Diagram)

Диаграмма состояний описывает жизненный цикл объекта «Игровая сессия» (Game Session):

- **Не начата** — головоломка загружена, но игрок ещё не сделал первый ход.
- **В процессе** — игрок решает головоломку. Таймер запущен.
- **Приостановлена** — игрок свернул приложение или нажал паузу. Таймер остановлен, прогресс сохранён.
- **Завершена успешно** — все клетки заполнены корректно. Результат записывается.
- **Завершена с ошибками** — игрок исчерпал допустимое количество ошибок (если такой режим включён).

Переходы между состояниями:
- «Не начата» → «В процессе»: игрок делает первый ход.
- «В процессе» → «Приостановлена»: игрок сворачивает приложение или нажимает паузу.
- «Приостановлена» → «В процессе»: игрок возвращается к игре.
- «В процессе» → «Завершена успешно»: все клетки заполнены верно.
- «В процессе» → «Завершена с ошибками»: превышен лимит ошибок.

## 2.3 Проектирование базы данных

Для хранения данных приложения спроектирована реляционная база данных. Выбор реляционной модели обусловлен характером данных: пользователи, головоломки, результаты и турниры связаны между собой чёткими отношениями, и реляционная модель наилучшим образом описывает эти связи.

В качестве СУБД для серверной части выбрана PostgreSQL. Это свободно распространяемая СУБД с открытым исходным кодом, которая хорошо зарекомендовала себя для веб-приложений и мобильных бэкендов. PostgreSQL поддерживает транзакции, индексы, JSON-поля и полнотекстовый поиск [источник: PostgreSQL 16 Documentation, The PostgreSQL Global Development Group, 2024].

На стороне клиента для локального хранения данных используется SQLite — встраиваемая СУБД, которая не требует отдельного сервера и идеально подходит для мобильных приложений.

## 2.4 Проектирование пользовательского интерфейса

Проектирование пользовательского интерфейса выполнялось с учётом рекомендаций Material Design (для Android) и Human Interface Guidelines (для iOS) [источник: Google Material Design Guidelines, 2024; Apple Human Interface Guidelines, 2024]. Это обеспечивает привычный пользователю опыт взаимодействия на каждой из платформ.

При проектировании интерфейса были определены следующие принципы:

**Минимализм.** Игровое поле — центральный элемент экрана. Все вспомогательные элементы (кнопки ввода цифр, подсказки, таймер) расположены так, чтобы не отвлекать от головоломки.

**Доступность в одно касание.** Любая ключевая функция (начать игру, получить подсказку, отменить ход) доступна за один-два нажатия. Глубокие вложенные меню не используются.

**Обратная связь.** Каждое действие пользователя сопровождается визуальной или тактильной реакцией: подсветка выбранной клетки, анимация при правильном решении, вибрация при ошибке (если включена в настройках).

### Структура экранов приложения

Навигация в приложении построена по принципу нижней панели (bottom navigation bar) с четырьмя разделами:

1. **Игра** — главный экран. Кнопка «Новая игра» с выбором сложности. Возможность продолжить незавершённую игру.
2. **Турниры** — список активных и предстоящих турниров. Результаты прошедших турниров.
3. **Профиль** — аватар, никнейм, рейтинг, статистика, достижения. Кнопка редактирования.
4. **Настройки** — выбор темы оформления, языка, звуков. Управление подпиской. Информация о приложении.

### Экран игрового процесса

Экран игры — самый важный экран приложения. Его компоновка:

- Верхняя часть: таймер и кнопка паузы.
- Центральная часть: игровое поле 9×9. Выбранная клетка и связанные строка, столбец и блок подсвечиваются. Одинаковые цифры подсвечиваются отдельным цветом для удобства.
- Нижняя часть: панель ввода с цифрами от 1 до 9, кнопки «Заметки», «Отменить», «Стереть», «Подсказка».

Цветовая палитра по умолчанию (светлая тема): белый фон поля, светло-голубая подсветка выделения, тёмно-синие предустановленные цифры, чёрные пользовательские цифры, красная подсветка ошибок.
